## 들어가며

보안 공부를 하다 보면 SQL Injection, XSS처럼 "어떤 값을 넣으면 뚫리는가"에 집중하게 된다. 그런데 2025년 11월에 공개된 OWASP Top 10:2025를 살펴보다가, 이상한 입력 하나 없이 정상적인 요청만으로도 서비스가 무너질 수 있다는 카테고리가 눈에 들어왔다. 바로 <strong>A06 Insecure Design(안전하지 않은 설계)</strong>이다.

이번 글에서는 A06이 무엇인지, 2021년과 비교해 어떻게 변했는지, 그리고 어떻게 막아야 하는지를 정리했다. 보안을 처음 접하는 사람도 읽을 수 있도록 최대한 쉽게 풀어 쓰려고 했다.

자료는 OWASP 공식 A06 페이지를 출발점으로 삼고, 그 페이지 하단 References에 연결된 자료들을 따라가며 확인했다. 공식 문서가 직접 추천한 자료만 사용했다는 뜻이다.

## 1. OWASP Top 10이란?

**OWASP**(Open Worldwide Application Security Project)는 웹 애플리케이션 보안 자료를 무료로 공개하는 비영리 커뮤니티다. 그중 가장 유명한 결과물이 **OWASP Top 10**으로, 여러 기업이 제공한 실제 취약점 데이터와 업계 설문을 바탕으로 "지금 웹 서비스에서 가장 중요한 보안 위험 10가지"를 정리한 문서다.

보통 4년 정도 주기로 개정되는데, 2021년판 이후 처음으로 2025년판이 나왔다.

| 순위 | 2021 | 2025 |
|---|---|---|
| 1 | Broken Access Control | Broken Access Control |
| 2 | Cryptographic Failures | Security Misconfiguration |
| 3 | Injection | Software Supply Chain Failures (신규) |
| 4 | Insecure Design | Cryptographic Failures |
| 5 | Security Misconfiguration | Injection |
| 6 | Vulnerable and Outdated Components | **Insecure Design** |
| 7 | Identification and Authentication Failures | Authentication Failures |
| 8 | Software and Data Integrity Failures | Software or Data Integrity Failures |
| 9 | Security Logging and Monitoring Failures | Security Logging and Alerting Failures |
| 10 | Server-Side Request Forgery | Mishandling of Exceptional Conditions (신규) |

두 목록을 나란히 놓고 보면 흐름이 보인다.

- **설정 실수(Security Misconfiguration)와 공급망(Software Supply Chain Failures)이 상위권으로 올라왔다.** 내가 직접 짠 코드보다, 어떻게 설정하고 무엇을 가져다 쓰는지가 더 큰 위험이 되었다는 뜻으로 읽힌다.
- **Injection이 3위에서 5위로 내려갔다.** 프레임워크와 ORM이 기본적으로 많은 부분을 막아주게 된 영향이라고 생각한다.
- **Insecure Design은 4위에서 6위로 내려갔다.** 하지만 이게 "덜 중요해졌다"는 뜻은 아니다. 이 부분은 3장에서 수치로 자세히 보겠다.

## 2. Insecure Design이란?

OWASP는 Insecure Design을 <strong>"보안 통제가 설계에 없거나, 있어도 효과가 없는 상태"</strong>로 정의한다. 여기서 중요한 건 이게 **코드를 잘못 짠 문제가 아니라는 점**이다.

### 설계 결함과 구현 결함은 다르다

OWASP는 두 가지를 분명히 구분한다. 원인도 다르고, 생기는 시점도 다르고, 고치는 방법도 다르다.

| 구분 | 구현 결함 | 설계 결함 |
|---|---|---|
| 언제 생기나 | 코드를 짤 때 | 요구사항을 정하고 설계할 때 |
| 원인 | 실수, 버그 | 무엇을 막아야 하는지 생각하지 않음 |
| 해결 | 코드 수정 | 설계 자체를 다시 해야 함 |

이걸 나는 **시험 문제**에 비유해서 이해했다.

- **구현 결함**은 수식은 맞게 세웠는데 계산하다가 실수한 경우다. 계산만 다시 하면 된다.
- **설계 결함**은 애초에 문제를 잘못 읽고 엉뚱한 식을 세운 경우다. 계산을 아무리 완벽하게 해도 답은 틀린다.

OWASP도 같은 말을 한다. 잘 설계된 시스템에도 구현 버그는 생길 수 있지만, **설계가 잘못된 시스템은 코드를 완벽하게 짜도 고칠 수 없다.** 막아야 할 보안 통제가 처음부터 만들어지지 않았기 때문이다.

### 대표적인 형태: 비즈니스 로직 결함

Insecure Design의 대표적인 예가 **비즈니스 로직 결함**이다. 요청 자체는 문법적으로 아무 문제가 없는 정상 요청인데, 서비스가 의도하지 않은 방식으로 기능을 악용하는 경우다. 예를 들어 "이 상태에서 저 상태로 넘어가면 안 된다"는 규칙을 아무도 정하지 않았다면, 개발자는 그걸 막는 코드를 짤 이유가 없다.

참고로 OWASP는 Insecure Design이 다른 모든 Top 10 항목의 근본 원인이라는 뜻은 아니라고 선을 긋는다. 설계 단계에서 생기는 문제만을 따로 묶은 카테고리라고 보면 된다.

## 3. 수치로 보는 2021 → 2025 변화

Insecure Design은 2021년에 처음 생긴 카테고리라서, 두 버전의 수치를 비교하면 4년 동안 무엇이 달라졌는지 볼 수 있다.

| 항목 | 2021 (A04) | 2025 (A06) |
|---|---|---|
| 순위 | 4위 | 6위 |
| 매핑된 CWE 수 | 40개 | 39개 |
| 최대 발생률 | 24.19% | 22.18% |
| **평균 발생률** | **3.00%** | **1.86%** |
| 평균 가중 익스플로잇 점수 | 6.46 | 6.96 |
| 평균 가중 영향도 점수 | 6.78 | 4.05 |
| 최대 커버리지 | 77.25% | 88.76% |
| 평균 커버리지 | 42.51% | 35.18% |
| 총 발생 건수 | 262,407건 | 729,882건 |
| 관련 CVE 수 | 2,691개 | 7,647개 |

> [!NOTE]
> CWE(Common Weakness Enumeration)는 취약점의 "유형"을 분류한 번호 체계이고, CVE는 실제로 발견된 개별 취약점에 붙는 번호다.

이 표에서 내가 읽은 동향은 세 가지다.

**첫째, 평균 발생률은 줄었다.** 3.00%에서 1.86%로 내려갔다. OWASP도 2021년에 이 카테고리를 만든 뒤 업계에서 위협 모델링과 안전한 설계를 더 중시하게 되면서 개선이 있었다고 설명한다. 카테고리를 만들어 이름을 붙인 것만으로도 사람들이 신경을 쓰기 시작했다는 점이 흥미로웠다.

**둘째, 그런데 발생 건수와 CVE 수는 오히려 약 2.8배 늘었다.** 발생률은 줄었는데 건수가 늘었다는 건, 수집된 데이터 규모 자체가 커진 영향이 크다고 본다. 또 2021년에는 새로 생긴 카테고리라 관련 CVE 매핑이 적었는데, 4년 동안 설계 결함으로 분류되는 실제 취약점이 계속 쌓였다는 뜻으로도 읽힌다. 즉 비율로는 좋아졌지만, 절대적인 양으로는 여전히 많이 발견되고 있다.

**셋째, 순위가 내려간 건 다른 항목이 치고 올라왔기 때문이다.** OWASP는 Security Misconfiguration(A02)과 Software Supply Chain Failures(A03)가 Insecure Design을 추월했다고 설명한다. Insecure Design이 사라지고 있는 게 아니라, 다른 위험이 더 빠르게 커졌다고 보는 게 맞다.

### OWASP가 강조하는 방향: Shift-Left보다 더 앞으로

2021년판과 2025년판 모두에서 OWASP는 같은 메시지를 반복한다. 흔히 말하는 **Shift-Left**(보안을 개발 초기로 당기기)를 코드 단계에서 멈추지 말고, **요구사항을 쓰고 설계하는 단계까지** 더 당겨야 한다는 것이다.

```text
[요구사항] → [설계] → [구현(코드)] → [테스트] → [운영]
     ^          ^          ^
     |          |          └ 기존의 Shift-Left (시큐어 코딩, 코드 리뷰)
     └──────────┴── A06이 말하는 출발점
```

## 4. 공격 시나리오로 이해하기

OWASP가 제시한 세 가지 시나리오를 보면 설계 결함이 무엇인지 더 쉽게 와닿는다.

### 시나리오 1: 비밀번호 찾기 질문

"출신 초등학교는?", "어머니 성함은?" 같은 질문으로 본인을 확인하는 방식이다. 문제는 **이 답을 나만 아는 게 아니라는 점**이다. 가족이나 친구, SNS를 조금만 찾아본 사람도 답을 알 수 있다.

질문과 답을 비교하는 코드는 완벽할 수 있다. 틀린 건 **"답을 안다 = 본인이다"라는 설계 전제**다. 그래서 NIST SP 800-63b와 OWASP ASVS 같은 기준에서는 이 방식을 쓰지 말라고 한다.

### 시나리오 2: 영화관 단체 예매

영화관이 "15명까지 단체 할인"이라는 정책을 만들었다. 그런데 공격자가 이 흐름을 분석해서 **요청 몇 번만으로 여러 극장의 좌석 수백 석을 한꺼번에 잡아둘 수 있는지** 시도한다. 성공하면 다른 손님은 표를 못 사고 영화관은 큰 매출 손실을 본다.

"한 번에 15명"이라는 규칙은 있었지만, **"한 사람이 동시에 잡을 수 있는 좌석의 총량"이라는 규칙은 아무도 정하지 않았다.** 설계에 없는 규칙은 코드에도 없다.

### 시나리오 3: 그래픽카드 리셀러 봇

인기 그래픽카드가 출시되자마자 리셀러가 봇으로 물량을 싹쓸이한다. 쇼핑몰 입장에서는 사람의 구매든 봇의 구매든 똑같은 구매 요청이라서, 처음부터 봇을 고려하지 않았다면 막을 방법이 없다.

OWASP는 "출시 몇 초 만에 들어온 구매"처럼 사람이 하기 어려운 패턴을 잡아내는 도메인 규칙과 봇 방어 설계로 이런 거래를 걸러낼 수 있다고 설명한다.

### 세 시나리오의 공통점

세 경우 모두 **코드는 시킨 대로 정확하게 동작했다.** 문제는 "무엇을 시킬지"를 정하는 단계에 있었다. 그래서 Insecure Design은 취약점 스캐너나 코드 리뷰만으로는 찾기 어렵다.

## 5. 어떻게 막을까: 위협 모델링

OWASP가 A06의 해결책으로 가장 강조하는 것이 <strong>위협 모델링(Threat Modeling)</strong>이다.

### 위협 모델링이란?

Threat Modeling Manifesto는 위협 모델링을 <strong>"시스템을 표현한 것(그림, 문서 등)을 분석해서 보안과 프라이버시 측면의 우려를 찾아내는 활동"</strong>으로 정의한다. 거창하게 들리지만, 결국 아래 네 가지 질문에 답하는 과정이다.

1. 우리는 무엇을 만들고 있나?
2. 무엇이 잘못될 수 있나?
3. 그에 대해 무엇을 할 것인가?
4. 충분히 잘했나?

Manifesto는 위협 모델링에서 중요하게 여겨야 할 가치도 다섯 가지로 정리하는데, 내가 이해한 대로 요약하면 이렇다.

- 체크리스트를 채우는 것보다 **설계 문제를 찾고 고치는 문화**
- 도구나 절차보다 **사람과 협업**
- 한 번의 점검보다 **계속 이해해 나가는 과정**
- 말로만 하는 것보다 **실제로 해보는 것**
- 한 번 만들고 끝내는 것보다 **계속 다듬는 것**

### STRIDE: "무엇이 잘못될 수 있나"를 찾는 체크리스트

2번 질문에 답할 때 자주 쓰는 체크리스트가 **STRIDE**다. OWASP SAMM도 위협 모델링의 기본 수준으로 STRIDE 같은 간단한 체크리스트를 쓰는 것을 예로 든다.

| 글자 | 위협 | 쉬운 설명 |
|---|---|---|
| S | Spoofing (위장) | 남인 척하기 |
| T | Tampering (변조) | 데이터 몰래 바꾸기 |
| R | Repudiation (부인) | 했는데 안 했다고 발뺌하기 |
| I | Information Disclosure (정보 노출) | 보면 안 되는 정보 보기 |
| D | Denial of Service (서비스 거부) | 서비스를 못 쓰게 만들기 |
| E | Elevation of Privilege (권한 상승) | 내 권한 이상의 일 하기 |

### 직접 적용해보기: 영화관 단체 예매

시나리오 2를 네 가지 질문으로 직접 분석해봤다.

**1. 무엇을 만들고 있나?**

```text
[사용자] --예매 요청--> [예매 서버] --좌석 확보--> [좌석 DB]
                            |
                            +--보증금 결제--> [결제 시스템]
```

**2. 무엇이 잘못될 수 있나?**

| STRIDE | 발생할 수 있는 위협 |
|---|---|
| S | 계정을 여러 개 만들어 다른 사람인 척 반복 예매 |
| T | 인원 수나 할인 여부 값을 클라이언트에서 조작해서 전송 |
| R | 예매 기록이 남지 않아 누가 좌석을 잡았는지 추적 불가 |
| I | 좌석 현황 조회로 다른 사람의 예매 정보 노출 |
| D | 결제 전 좌석 임시 확보를 반복해서 모든 좌석 선점 (핵심 위협) |
| E | 일반 회원이 관리자용 할인 기능 호출 |

**3. 무엇을 할 것인가?**

- 사용자와 결제수단 기준으로 동시에 잡을 수 있는 좌석 총량 제한
- 임시 확보한 좌석에 만료 시간을 두고, 시간 안에 결제하지 않으면 자동 해제
- 인원 수와 할인 여부는 서버에서 다시 검증
- 짧은 시간에 대량 예매가 들어오는 패턴 탐지

**4. 충분히 잘했나?**

- "한 사용자가 여러 극장에 15석씩 100번 요청"하는 상황을 테스트로 만들어서 실제로 막히는지 확인

직접 해보니, 4가지 질문 중 가장 어려운 건 2번이었다. 정상적으로 쓰는 방법만 생각하던 머리를 "나쁜 마음을 먹은 사용자라면 어떻게 할까"로 바꾸는 게 생각보다 쉽지 않았다. STRIDE 같은 체크리스트가 필요한 이유가 여기 있다고 느꼈다.

## 6. 위협 모델링 말고도 해야 할 것들

OWASP A06 페이지와 거기서 연결된 자료들이 공통으로 말하는 방어책을 단계별로 정리했다.

### 요구사항 단계: 무엇을 지킬지 먼저 정하기

- 데이터마다 기밀성, 무결성, 가용성, 인증성 중 무엇이 중요한지 **비즈니스 담당자와 함께** 정한다.
- 보안에 들어갈 예산과 시간을 설계부터 운영까지 **처음부터 계획에 넣는다.**
- OWASP Secure Product Design 치트시트는 이 과정을 두 단계로 나눈다.
  - **제품 구상 단계**: 비즈니스 영향 평가로 제품에 필요한 보안 수준을 정한다.
  - **제품 설계 단계**: 위협 모델링 결과를 보안 관련 유저 스토리로 만들어 개발 작업마다 추가한다.

### 설계 단계: 검증된 원칙 따르기

Secure Product Design 치트시트와 OWASP SAMM의 Secure Architecture 항목에 반복해서 나오는 원칙들이다.

- **안전한 기본값**: 아무 설정도 하지 않았을 때 가장 안전한 상태여야 한다.
- **공격 표면 최소화**: 외부에 노출되는 기능, API, 포트를 최소한으로 줄인다.
- **안전한 실패**: 에러가 나면 문이 열리는 게 아니라 닫히는 쪽으로 동작해야 한다.
- **최소 권한**: 필요한 만큼만 권한을 준다.
- **심층 방어**: 한 겹이 뚫려도 다음 겹이 막도록 여러 겹으로 방어한다.

여기에 OWASP는 검증된 보안 설계 패턴과 **paved road(포장된 길)** 컴포넌트를 만들어 재사용하라고 권한다. 매번 인증이나 권한 체크를 새로 짜는 대신, 이미 검증된 길을 따라가라는 뜻이다.

### 구조, 테스트, 문화

- 프론트엔드부터 백엔드까지 **모든 계층에서 값이 말이 되는지 검사**한다.
- 노출 정도에 따라 시스템과 네트워크 계층을 나누고, 여러 고객이 같은 시스템을 쓰는 서비스라면 **고객 간 분리를 설계 단계부터** 넣는다.
- 정상적인 사용(use case)뿐 아니라 **악용 사례(misuse case)도 테스트**한다.
- 보안을 나중에 붙이는 도구가 아니라 **팀의 문화**로 만든다. 위협 모델링 자체를 개발자 교육 도구로 쓰는 것도 방법이다.

## 마치며

A06을 공부하면서 가장 크게 바뀐 생각은 <strong>"취약점은 코드에만 있는 게 아니다"</strong>라는 점이다.

지금까지 웹 해킹을 공부할 때는 어떤 입력을 넣으면 필터를 우회할 수 있는지에 집중했다. 그런데 Insecure Design은 이상한 입력이 전혀 없어도, 정상적인 기능을 정상적인 방법으로 쓰는 것만으로 문제가 생길 수 있다는 걸 보여준다. 코드는 아무 잘못이 없고, 빠진 건 "이걸 누가 나쁘게 쓰면 어떻게 될까"라는 질문 하나였다.

2021년에서 2025년 사이의 수치를 보면 희망적인 부분도 있다. 카테고리가 생기고 위협 모델링이 알려지면서 평균 발생률이 실제로 줄었다. 반대로 발견되는 절대량은 여전히 늘고 있어서, 아직 갈 길이 멀다는 것도 보여준다. 특히 이번 2025년판에서 설정 실수와 공급망이 위로 올라온 걸 보면, 보안의 범위가 "내가 짠 코드"에서 "내가 설계하고, 설정하고, 가져다 쓴 모든 것"으로 넓어지고 있다는 게 느껴진다.

앞으로 프로젝트를 할 때는 기능 명세를 쓰는 단계에서 위협 모델링의 네 가지 질문을 같이 적어보려고 한다. 거창한 도구 없이 질문 네 개만으로도, 코드를 짜기 전에 막을 수 있는 문제가 생각보다 많다는 걸 이번에 배웠다.
