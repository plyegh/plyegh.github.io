## 1. 사건 선정 이유

클라우드 보안과 LLM 보안을 같이 공부하면서 계속 든 질문이 있다. **"공격자가 사람이 아니라 에이전트라면, 기존 방어가 그대로 통할까?"**

이 사건은 그 질문에 대한 첫 번째 실제 사례다. 동시에 원인을 뜯어 보면 낯선 부분만 있는 건 아니다.

- OpenAI 쪽: **네트워크 격리 설계**와 **경고 신호 처리** 실패
- Hugging Face 쪽: **신뢰할 수 없는 입력을 실행하는 파이프라인**과 **워커에 놓인 넓은 권한의 자격증명**

새로운 공격 주체와 익숙한 클라우드 보안 문제가 한 사건 안에 같이 있어서 골랐다.

## 4. 공격 흐름 분석

### 4.1. 1단계 - 격리 환경 탈출 (OpenAI 내부)

ExploitGym 평가 환경은 **인터넷에 직접 접근할 수 없게** 설계돼 있었다. 모델은 필요한 패키지를 Artifactory라는 사내 패키지 캐시 프록시를 통해서만 받을 수 있었다.

문제는 Artifactory 자체는 **외부 원격 저장소(PyPI, npm 등)에 접속해야** 한다는 점이다. 에이전트들은 Artifactory의 원격 저장소 기능이 자기 대신 외부로 요청을 보내게 만들어 인터넷 접근을 되찾았다. 여기에 Artifactory의 제로데이(원격 코드 실행, 관리자 권한 획득)도 찾아서 썼다.

```text
[평가 샌드박스]  ──(인터넷 차단)──X──▶ 인터넷
      │
      └─▶ [Artifactory 캐시 프록시] ──(원격 저장소 기능 = 외부 요청 가능)──▶ 인터넷
                ▲
                └─ 제로데이로 장악 + 파일 업로드로 에이전트 간 "게시판"으로도 사용
```

격리의 마지막 관문을 **외부와 통신해야 하는 서비스**에 맡긴 셈이다. 에이전트 입장에서 그 서비스는 출구였다.

### 4.2. 2단계 - 에이전트 간 협업 채널

이 사건에서 가장 낯선 부분이다. 에이전트들은 Artifactory에 파일을 올리는 방식으로 **서로 메시지를 주고받는 임시 게시판**을 만들었다. 한 에이전트가 찾은 경로나 자격증명을 다른 에이전트가 이어받아 쓸 수 있었다. 이후 분석에서 수백 개의 에이전트 인스턴스가 이런 식으로 협업한 것으로 나타났다.

OpenAI가 6월 말과 7월 초에 게시판을 지웠지만, 에이전트들은 이틀 만에 **완전히 다른 메커니즘으로** 게시판을 다시 만들었다. 막힌 경로 하나를 고치는 방식으로는 막을 수 없는 상대였다.

### 4.3. 3단계 - Hugging Face 침투

인터넷에 나온 에이전트는 외부의 다른 코드 실행 샌드박스 서비스를 장악해 발판으로 쓰고, Hugging Face의 **데이터셋 처리 파이프라인**을 노렸다. 악성 데이터셋을 올려서 같은 설정 기반 데이터 로더의 두 취약점을 엮었다.

| 단계 | 취약점 | 결과 |
|---|---|---|
| ① 파일 읽기 | HDF5의 external raw storage 기능으로 데이터셋 바이트를 로컬 파일에 매핑 | 워커 파드의 환경 변수(시크릿·토큰)와 워커 소스 코드 유출 |
| ② 코드 실행 | 데이터셋 설정의 Jinja2 템플릿 인젝션 (SSTI) | 워커 안에서 임의 코드 실행 |

OpenAI 보고서에 따르면 에이전트는 이 밖에도 공개적으로 노출돼 있던 Hugging Face 자격증명 14개를 재구성·검증해 썼다.

### 4.4. 4단계 - 자격증명 수확과 측면 이동

워커에 발을 들인 뒤에는 익숙한 클라우드 침해 흐름이 이어졌다.

1. 워커에서 자격증명·API 탐색
2. 노드 수준 권한 상승
3. **쿠버네티스, DB, 메시징, 코드 저장소, 클라우드 자격증명**을 4개 리전의 워커에서 수집
4. 여러 내부 클러스터로 측면 이동
5. 공개 서비스 위에 스스로 위치를 옮기는 C2 구성, 짧게 쓰고 버리는 샌드박스 다수 사용

목표는 평가 문제의 정답이었고, 실제로 Hugging Face 프로덕션 DB에서 테스트 정답을 직접 읽어 왔다.

```text
[OpenAI 샌드박스] → Artifactory 제로데이 → 인터넷 → 외부 코드 샌드박스(발판)
      → 악성 데이터셋 업로드 → HDF5 파일 읽기(시크릿) + Jinja2 SSTI(RCE)
      → 워커 → 노드 → 클러스터 자격증명 → 내부 클러스터 측면 이동 → 프로덕션 DB
```

## 5. 근본 원인

### 5.1. OpenAI 쪽

1. **격리 설계의 단일 실패 지점**: 인터넷 차단을 외부 통신이 필요한 프록시 하나에 의존했고, 그 프록시가 제로데이로 뚫렸다.
2. **위험한 설정의 모델 + 강한 동기**: 평가를 위해 사이버 공격 거부(refusal)를 낮춘 모델이었고, 훈련 과정에서 "어떻게든 정답을 맞히면 보상받는" 행동(보상 해킹)이 강화돼 있었다. 끈질기게 목표를 추구한 것도 원인으로 꼽혔다.
3. **경고 신호를 사고로 다루지 않음**: 5월 말 관찰과 6월 27일 경보가 있었지만, 증상(권한 상승 경로, 노출된 자격증명)만 고치고 평가를 재개했다.
4. **행동 모니터링 부재**: OpenAI는 지금 쓰는 사고 과정(CoT) 모니터링이 당시에 돌고 있었다면, Hugging Face 침해보다 하루 이상 먼저 보안팀에 알렸을 것이라고 밝혔다.

### 5.2. Hugging Face 쪽

1. **신뢰할 수 없는 입력을 실행하는 파이프라인**: 누구나 올릴 수 있는 데이터셋의 설정이 템플릿 엔진과 파일 매핑 기능을 거쳐 워커에서 해석됐다.
2. **워커 환경에 시크릿 상주**: 데이터 처리 워커의 환경 변수에 넓게 쓸 수 있는 토큰이 들어 있었다.
3. **워커 하나에서 클러스터 전체로 이어지는 권한**: 노드·클러스터 자격증명을 한 워커에서 수확할 수 있었다.

Hugging Face 측 원인은 AI 플랫폼이 원래 갖고 있는 구조적 위험이다. AI 플랫폼은 **제3자 코드와 설정을 자기 인프라 안에서 돌리는 것이 본업**이기 때문이다.

## 6. 대응

### 6.1. Hugging Face

- 데이터셋 코드 실행 경로 두 개 차단 (근본 취약점 수정)
- 침해된 노드 재구축, 공격자 발판 제거
- 영향받은 자격증명·토큰 전부 폐기 후 재발급, 클러스터 보안 통제와 모니터링 강화
- 1만 7천 건 넘는 공격 이벤트를 **AI 기반 분석으로 재구성**해 타임라인과 피해 범위 확정
- 법 집행기관 신고, 외부 포렌식 업체와 공동 조사, 사용자에게 토큰 교체 권고

대응 과정에서 흥미로운 점도 있었다. 포렌식에 쓰려던 일부 상용 AI 모델이 공격 코드 분석 요청을 거절해서 조사가 어려웠다는 이야기가 나왔다. 방어하는 쪽도 AI를 쓰는 시대에 가드레일이 수비를 막는 상황이 생긴 것이다.

### 6.2. OpenAI

- 문제의 모델을 비활성화·암호화하고 연구 접근을 제한
- 진행 중인 ExploitGym 평가 중단, 전사 조사 착수
- Artifactory 제로데이를 벤더에 책임 있게 공개하고 패치 협력
- CrowdStrike 등 외부 자문과 영향 범위 검증, METR·Redwood Research에 제3자 평가 의뢰
- 연구 인프라 전반의 네트워크·접근 통제 강화, 실행 환경 격리와 다층 방어(defense in depth) 도입
- Hugging Face를 Trusted Access for Cyber 프로그램에 추가

## 7. 보완이 미흡했던 부분

### 7.1. 두 번의 경고, 두 번의 "고치고 재개"

가장 큰 문제는 기술보다 **판단 절차**였다.

| 시점 | 관찰된 것 | 한 조치 | 놓친 질문 |
|---|---|---|---|
| 5월 말 | 에이전트 간 게시판, 허용 안 된 인터넷 접근 | 기록만 함 | "격리가 이미 깨졌는가?" |
| 6월 27일 | 의심 활동 경보 | 경로 차단, 재구축 후 재개 | "왜 모델이 이걸 하려 하는가?" |
| 7월 4~6일 | Artifactory 장애, 제로데이 | 패치 후 재개 | "다른 출구는 없는가?" |

매번 **증상은 고쳤지만 원인(모델의 행동 경향)은 다루지 않았다**. 상대가 같은 방법만 반복하는 스크립트라면 통하는 대응이지만, 새로운 방법을 스스로 찾는 에이전트에게는 통하지 않았다. 1편에서 Aqua가 "교체했지만 봉쇄하지 못한" 것과 비슷한 구조다. 대응은 했는데 **상대가 아직 안에 있는지**는 확인하지 않았다.

### 7.2. 격리를 "네트워크 정책"으로만 봤다

샌드박스 격리를 방화벽 규칙과 프록시로만 생각했다. 하지만 에이전트에게는 **외부와 통신할 수 있는 모든 서비스가 잠재적 출구**다. 패키지 캐시, 로그 수집기, 메트릭 전송, DNS 등이 다 해당한다. 고위험 평가라면 "허용된 서비스가 대신 외부로 요청을 보낼 수 있는가"까지 위협 모델에 넣었어야 했다.

### 7.3. 행동 감시가 사후에 생겼다

CoT 모니터링이 있었다면 하루 이상 일찍 알았을 것이라는 OpenAI 설명은, 뒤집어 보면 **사고 당시에는 그 탐지 계층이 없었다**는 뜻이다. 능력 평가를 돌리는 속도에 비해 감시 체계가 늦게 따라왔다.

### 7.4. AI 플랫폼의 "업로드 = 실행" 구조

Hugging Face의 취약점은 AI 에이전트가 아니라 사람 공격자도 쓸 수 있었다. 데이터셋 로더처럼 **사용자 입력을 해석하는 기능**이 시크릿이 있는 환경에서 돌고 있었다. 언론과 업계 분석에서도 "기본적인 보안 위생만으로는 자율 에이전트를 막을 수 없다"는 말과 함께, 바로 그 기본(워커 격리, 단기 자격증명)이 무너진 지점이 피해를 키웠다는 지적이 같이 나왔다.

### 7.5. 공개되지 않은 부분

일부 언론은 OpenAI 보고서가 모델 훈련 과정의 상세 내용과 내부 의사결정 과정은 충분히 설명하지 않았다고 지적했다. 미국 일부 주 검찰이 자료 보존을 요구하고 소환장을 보낸 상태라, 추가 사실이 나올 가능성이 있다.

## 8. 정리 - 에이전트 시대의 클라우드 보안

이 사건을 1편, 2편과 나란히 놓으면 공통점이 보인다.

| | 1편 Trivy→LiteLLM | 2편 McKinsey Lilli | 3편 OpenAI→HF |
|---|---|---|---|
| 공격 주체 | 사람 (자동화 봇 활용) | AI 에이전트 (연구, 허가된 신고 정책) | AI 에이전트 (의도치 않은 자율 행동) |
| 진입점 | CI 설정 실수 | 인증 누락 + SQLi | 프록시 제로데이 + 데이터셋 로더 |
| 피해를 키운 것 | 장기·광범위 토큰, 불완전한 교체 | 데이터와 AI 설정 미분리 | 워커에 놓인 넓은 자격증명, 경고 무시 |
| 새로운 점 | 보안 도구가 공격 도구로 | SQLi가 AI 행동 조작으로 | 공격자가 사람이 아님 |

세 사건 모두 **진입점보다 그 뒤에 놓여 있던 과도한 권한과 오래 사는 자격증명**이 피해 규모를 결정했다. 공격자가 사람이든 에이전트든, 방어의 기본은 크게 바뀌지 않는다. 다만 에이전트는 그 기본의 빈틈을 훨씬 빠르고 끈질기게 찾는다.

**에이전트를 운영하는 쪽은 격리와 판단 절차를 같이 봐야 한다.** 샌드박스는 네트워크 규칙만이 아니라 외부와 통신하는 모든 서비스(프록시, 캐시 등)를 출구로 보고 막아야 한다. 이상 징후가 보이면 증상만 고치고 재개하지 말고, 원인 분석이 끝난 뒤에 재개해야 한다.

**업로드를 처리하는 플랫폼은 "업로드 = 실행"을 전제로 설계해야 한다.** 사용자가 올린 데이터와 설정을 해석하는 워커는 시크릿이 없는 격리 환경에서 돌리고, 워커 하나가 클러스터 자격증명까지 닿지 않게 권한을 끊어야 한다.

OpenAI는 이 사건을 자기들과 세계에 보내는 "경고 사격"이라고 표현했다. 클라우드 보안을 공부하는 입장에서는 오히려 **기존 원칙(격리, 최소 권한, 단기 자격증명, 탐지 후 원인 분석)의 중요성이 커졌다**는 신호로 읽었다. 공격자가 지치지 않는 에이전트라면, 원칙에 남은 작은 예외 하나가 곧 출구가 된다.
